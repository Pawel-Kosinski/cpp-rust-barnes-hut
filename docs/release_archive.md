# Version 1.2.0 archive and computational provenance

Version-specific DOI: https://doi.org/10.5281/zenodo.23286007

GitHub release: https://github.com/Pawel-Kosinski/cpp-rust-barnes-hut/releases/tag/v1.2.0

## Two complementary archives

- `BHBench-CR-v1.2.0-source.zip`: the unmodified GitHub source ZIP downloaded
  from the final v1.2.0 tag, with its original top-level directory retained.
- `BHBench-CR-v1.2.0-experimental-data.zip`: exact publication inputs and
  complete experimental evidence, preserving paths relative to the repository
  root, plus a SHA-256 file manifest. This is required for the recorded-data
  audits; Git alone intentionally excludes large inputs and binary payloads.

Extract the source ZIP first. Extract the data ZIP into that extracted source
directory so that its `results/` directory joins the source's `results/`.
Any overlapping file must be byte-identical; stop on a conflicting file rather
than silently replacing it. Verify the data archive's `SHA256SUMS.txt` before
running the audit commands documented in each campaign README.

The data archive must contain all 22 extended-campaign inputs and the full
`extended-2026-10-08`, `laptop-2026-10-09`, and
`laptop-performance-2026-10-09` directories under `results/manuscript/`.
This includes the computational source ZIP, manifests, raw logs, force/state
outputs, analyses, both complete laptop payloads, executables, DLLs and their
licenses. It must also retain the five byte-identical historical publication
inputs under `results/manuscript/v1.1.3/fig1`, `fig2` and `fig3`, with hashes
listed in that campaign's README and environment records.
The companion archive is not merely the old five-input asset.

## Measured source versus release metadata

The extended measurements used a development snapshot based on commit
`343749d3124d5ee44b8fdf1c296a66df3df4eb7e`. The exact computational identity
is the 22-file `source_identity.json`, not that base commit alone.
`computational_source.zip` preserves those original files, including Cargo
manifests with package version 1.1.5. Its SHA-256 is
`c50e9a9aadf51b0c57d8ec82983fca2f66d8a3e808a1a0ad456e27ea0194c1ff`.

The release Cargo manifests label the package 1.2.0. Only that package-version
field differs from the frozen computational manifests; solver code and locked
dependency identities are unchanged. Recorded executable hashes continue to
identify the original measured binaries. Rebuilding a release is not a claim
to have regenerated byte-identical executables or repeated the timings.

Frozen laptop payloads and raw run metadata intentionally retain their original
pre-release labels and local paths. Never bulk-replace version strings or DOI
references inside them. Campaign READMEs describe their inclusion in 1.2.0;
the frozen evidence documents what actually ran.

The three new campaign directories have `-text` entries in `.gitattributes`.
This prevents Git's Windows newline conversion from changing manifest-covered
files, including CRLF launchers and raw logs. Do not normalize their line endings.

## Publication order

Reserve the DOI, complete all metadata, then commit the approved branch.
After the repository owner approves the merge, tag the reviewed commit and
publish the GitHub release. Download that tag's source ZIP once and preserve
its bytes when naming and uploading the Zenodo asset. Verify both archives
and their hashes before publishing the reserved Zenodo version. Do not move
the tag, rebuild the source ZIP from a later working tree, or replace an asset
after publication to update metadata. Historical tags and records remain intact.
